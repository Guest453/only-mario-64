    How one Mario becomes everybody's Mario

    The engine here is the Super Mario 64 decompilation compiled to WebAssembly. It has no netcode and exposes no game-state hooks, and Discord's Activity sandbox blocks WebRTC. So instead of pretending we can spawn your friends inside Bob-omb Battlefield, this Activity does the one thing that genuinely works with N players and one save file: it shares the controller.

    Keys (this build)

    ↑ ↓ ← → / WASDanalog stick — walk, climb, swim
    XA — jump, kick, wall jump
    CB — punch, dive, grab, read signs
    SpaceZ — crouch, long jump, ground pound
    EnterStart — pause, menus, going through doors

    There is no keyboard camera in this port: Mario turns, the camera follows. Gamepads work natively for the host and are mapped into the shared pad for everyone else.

    Modes

      What Discord gives us

      • Identity — the READY payload carries your id / username / avatar hash, and getInstanceConnectedParticipants() returns everyone in the instance. No OAuth, no account linking, no API key.
      • The room — instanceId is identical for everyone who joined the same Activity in the same voice channel, and dies when they all leave. That is the room code.
      • Invites — openInviteDialog() for the channel, shareLink() for a deep link.
      • Layout — ACTIVITY_LAYOUT_MODE_UPDATE tells us when we are in PIP or a grid tile, and the chrome shrinks instead of overflowing.
      • Presence — setActivity() writes “Playing SM64 with 4 others” if you ship an optional token exchange endpoint (see docs/SDK-NOTES.md).

      What Discord does not give us

      Any transport for game state. Traffic leaves the iframe through Discord's proxy (Cloudflare Workers): HTTP ✅, WebSocket ✅, WebTransport ⏳, WebRTC ❌. Multiplayer therefore runs on the small WebSocket relay in relay/server.js, routed through a /relay URL mapping. No relay reachable ⇒ everyone plays their own copy and the lobby degrades to presence-only, on purpose.
