# Wire protocol — v1

Defined once, in [`src/protocol.js`](../src/protocol.js), and implemented
independently on both sides: [`src/net.js`](../src/net.js) (client) and
[`relay/server.js`](../relay/server.js) (server). Text frames are JSON objects
with a one-letter type tag `t`; video is a binary frame. This document is the
contract — `test/relay.test.mjs` fails if the two drift apart.

## Connect

```
ws://host/ws?room=<key>&name=<display name>&id=<discord snowflake>&av=<avatar hash>&plat=desktop&ready=1
```

* `room` (or `instance_id`) is lowercased, filtered to `[a-z0-9_-]` and capped at
  40 chars; empty ⇒ `lobby`. Inside Discord it is `sdk.instanceId`, so the voice
  channel *is* the room.
* Everything else in the query string is **display data**, stored as-is and
  broadcast. The relay authenticates nobody — see "Trust" at the bottom.
* Other params: `name` ≤24 chars, `id` ≤32, `av` ≤64, `plat`, `ready=1`.

You are welcomed the moment the 101 lands — there is no auth round trip:

```jsonc
{ "t": "welcome", "ver": 1, "room": "lobby", "you": "lC96Vz-d", "sid": "lC96Vz-d",
  "host": "lC96Vz-d", "players": [ /* see roster */ ], "state": { "mode": "solo", "opts": {} },
  "vote": null, "maxPlayers": 8 }
```

`you` is a 6-byte base64url connection id generated by the relay. It is **not**
the Discord user id: one person can hold two connections (two tabs), and the
session belongs to the connection that currently has an engine.

## Client → relay

| `t` | payload | relay action |
| --- | --- | --- |
| `hello` | `ver, room, ready, plat, watch` | version ≠ 1 ⇒ `err:version` + drop; otherwise adopt `ready`/`plat`/`watch` and re-broadcast the roster |
| `in` | `s` (bits, masked to 16), `f` (client frame no.) | stores `player.bits`; forwards to the **host only** as `input` |
| `ready` | `ready: bool` | engine loaded/unloaded → re-elect host, broadcast roster |
| `watch` | `on: bool` | this player now wants the host's frames (see frames) |
| `state` | `s: {mode, opts, rot, pad, padUntil}` | **host only** (`err:not_host`), merge into room state, broadcast roster |
| `profile` | `name, id, av` | update display fields, broadcast roster |
| `chat` | `m` | strip control chars, trim to 240, 3 per 10 s, fan out |
| `vote` | `kind` (default `mode`), `value`, `opts?` | open an 8 s ballot; `err:rate_limited` if one is running |
| `vote_ballot` | `yes: bool` | set/flip this player's ballot, re-broadcast `vote_new` |
| `promote` | `cid` | **host only**: pin a new host (target must be `ready`) |
| `ping` | `c` (client ms) | reply `pong` with the same `c` |
| `leave` | — | marks `left` so the tally stops counting you before your socket dies |
| *binary* | `SM6F` frame | accepted **only from the host**; fanned out to `watching` players |

Unknown `t` values are ignored (forward-compatible).

## Relay → client

| `t` | payload |
| --- | --- |
| `welcome` | as above |
| `roster` | `{host, players[], state}` — on every membership, flag, state or profile change |
| `input` | `{from, s, f}` — to the host only |
| `chat` | `{from, name, m, ts}` |
| `vote_new` | `{kind, value, by, name, need, endsAt, yes[], no[]}` |
| `vote_end` | `{kind, value, by, yes[], no[], need, passed}`; a passed `mode` motion also writes room state and re-broadcasts `roster` |
| `promoted` | `{cid}` — to the requester, confirming the pin |
| `pong` | `{c, ts}` — RTT = `Date.now() - c` |
| `err` | `{code, msg}`, codes: `version`, `room_full` (+`max`), `not_host`, `no_host`, `bad_message`, `rate_limited` |
| *binary* | the host's `SM6F` frame, byte-for-byte |

`players[]` entries are `{cid, id, name, av, plat, ready, host, watching, bits}`.
`host` is `cid === room.host`, computed at broadcast time — there is exactly one
per room, or `null` while nobody ready is connected.

## Controller bits

16 bits, `|`-combined (`src/protocol.js` → `BTN`, `CODE_TO_BITS`), matching what
the engine's SDL keyboard state is translated from:

```
0x0001 UP     0x0002 DOWN   0x0004 LEFT   0x0008 RIGHT
0x0010 A      0x0020 B      0x0040 Z     0x0080 START
0x0100 L     0x0200 R      0x0400 C_UP  0x0800 C_DOWN
0x1000 C_LEFT 0x2000 C_RIGHT              0xC000 unused
```

Co-op groups (`GROUPS`) partition the same 16 bits four ways — `stick`, `A`,
`BZ`, `menu` — which is why mode arbitration can hand out slices without anyone
inventing a second protocol.

## Binary video frame (`SM6F`)

```
0   4  bytes  magic 0x534D3646 "SM6F"
4   4  u32    index     — host frame counter, wraps; viewers count holes
8   4  u32    ts         — ms since the host started streaming (→ latency)
12  n  bytes  JPEG
```

No width/height/fps fields: the viewer's canvas is fixed aspect and the JPEG
carries its own size, so header space would be pure overhead. `decodeFrame`
returns a *view* (`new Uint8Array(buf, 12)`), not a copy — a 20 KB alloc per frame
per viewer is waste nobody needs.

The stream is **drop-first by design**: the host skips encoding entirely when its
own uplink is backing up (`bufferedAmount > 512 KB`) and skips any viewer whose
socket is still draining, and the relay never queues video behind video. Live
Mario at 8 fps beats Mario from three seconds ago at 30 fps.

## Room state and votes

`state` is a flat object the host owns: `{mode, opts, rot, pad, padUntil}`.
Anyone may *ask* for a change by calling a vote; the relay tallies after 8 s and
needs `max(2, floor(eligible/2)+1)` yes votes from players in the room —
strictly more than half, so two players can never outvote a third. On a passed
`mode` motion the **relay** writes the state itself (not the winning client), so
every member — including players who join later, see `welcome.state` — agrees
without anyone having to trust a peer.

## Trust

The relay does not verify Discord identities. `id`/`name`/`av` are claims made by
a socket, and inside Discord anyone who can open devtools in the iframe can forge
them; through the proxy, `forwarded` headers are Discord's and are not checked by
us either. That is deliberate: the pad is the only shared resource, the host
arbitrates it, and a griefer hurts the room they are standing in.

Do not build anything on top of v1 that needs a verified user — leaderboards,
scores, moderation actions, "host privileges" that matter. For that, add the
optional bearer from [ACTIVITY-AUTH.md](./ACTIVITY-AUTH.md) and check it in
`attach_()` / `handleText()`.
